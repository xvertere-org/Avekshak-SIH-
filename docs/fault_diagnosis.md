# Phase 8 — Supervised Fault Diagnosis with XGBoost

## 1. Objective & Scope

Phase 8 implements the fault classification layer of the SIH26054 predictive health monitoring (PHM) system.

While Phase 7 answers:
> **"Is the engine behaving abnormally?"** (Binary / Unsupervised Anomaly Detection)

Phase 8 answers:
> **"What is the most likely fault causing the abnormal behavior?"** (Supervised Multiclass Fault Diagnosis)

Phase 8 maps physical deviations captured in normalized residual channels and flight context into a discrete fault identity drawn from a physics-grounded taxonomy.

> [!IMPORTANT]
> **Validation Boundary:** Phase 8 is trained and evaluated strictly on physics-informed synthetic aero-piston telemetry generated by the project digital twin and simulator. High synthetic-data performance does **not** establish real-world MALE-UAV flight-data fault classification validity.

---

## 2. Canonical Fault Taxonomy (6 Classes)

The fault taxonomy is sourced directly from [`simulator.fault_interface.FaultType`](file:///d:/NIRVANAA-SIH-SUBMISSION/simulator/fault_interface.py#L21-L30). The 6 canonical target classes (and their alphabetical index order) are:

| Index | Canonical Label String | Description | Physical Manifestation |
|---|---|---|---|
| 0 | `cooling_degradation` | Radiator / cooling jacket degradation | CHT rise, Oil Temp secondary rise |
| 1 | `fuel_injection_abnormality` | Lean / rich mixture drift | EGT surge / drop, fuel flow discrepancy |
| 2 | `lubrication_degradation` | Oil pump / viscosity failure | Oil pressure drop, Oil Temp elevation |
| 3 | `mechanical_degradation` | Piston / bearing / mount wear | 1x / 2x harmonic vibration surge |
| 4 | `none` | Nominal baseline operation | Residuals centered near zero |
| 5 | `sensor_fault` | Telemetry channel failure | Single-channel bias, drift, noise, stuck, dropout |

The Phase 1 `FaultCategory` enum in `telemetry/schema.py` is stale and retained solely for backward compatibility; Phase 8 uses only `FaultType`.

### 3.2 Sensor Fault Treatment
Sensor channels (7) and failure modes (5) are **generation factors**, not classification labels. All 91 sensor-fault runs share the single classification target `"sensor_fault"`.

## 4. Feature Design & Leakage Prevention

### 4.1 Feature Schema (Exactly 16 Columns)

The classifier operates on a 16-feature vector consisting of 7 core diagnostic signals and 9 operating context signals:

1. **Normalized Residuals (7 Core Features):**
   - `rpm_norm_residual`
   - `cht_norm_residual`
   - `egt_norm_residual`
   - `oil_temp_norm_residual`
   - `oil_pressure_norm_residual`
   - `fuel_flow_norm_residual`
   - `vibration_norm_residual`

2. **Continuous Operating Context (3 Features):**
   - `throttle`
   - `altitude`
   - `load`

3. **One-Hot Encoded Mission Phase (6 Features):**
   - `phase_TAKEOFF`
   - `phase_CLIMB`
   - `phase_CRUISE`
   - `phase_LOITER`
   - `phase_DESCENT`
   - `phase_LANDING`

### 4.2 Deterministic Unseen Category Handling
If `transform()` encounters an unknown or unseen flight phase at inference time, all 6 one-hot columns are deterministically set to `0`. The 16-column schema defined at training time remains immutable and will never throw a runtime error.

### 4.3 Strict Leakage Prevention
The following fields are strictly excluded from classifier inputs:
- `fault_type` (Target label)
- `generation_severity`, `generation_sensor_channel`, `generation_sensor_mode` (Generation metadata)
- `FaultState.parameters` (Simulator internal state)
- Phase 7 `anomaly_status`, `anomaly_score`, detector scores
- Future telemetry observations

## 5. Mission-Aware Data Splitting

Telemetry samples within a single flight are temporally correlated. Random sample-level splitting would leak information across adjacent seconds.

Phase 8 uses **Grouped Stratified Splitting** grouped by `mission_run_id`:
- **Split Unit:** `mission_run_id`
- **Ratio:** 70% Train (~84 runs) / 15% Validation (~22 runs) / 15% Test (~18 runs)
- **Stratification:** Carried out independently per fault class to ensure every class has ≥1 run in every split.
- **Guarantee:** No `mission_run_id` ever appears across multiple splits.

> [!WARNING]
> **Single-Trajectory Evaluation Limitation:** For physical fault classes with 6 total runs, the 15% test split contains exactly 1 independent trajectory (~1,720 samples). While this yields thousands of sample-level evaluations, they originate from a single flight profile.

---

## 6. Class Imbalance Mitigation

With 91 sensor-fault runs versus 6 runs for other classes, `sensor_fault` would naturally dominate loss gradients.

- **Mitigation:** Inverse class frequency sample weighting:
  $$\text{weight}_c = \frac{N_{\text{total}}}{K \times N_c}$$
- **Scope:** Weights are applied **only during training** via XGBoost's `sample_weight`.
- **Integrity:** Validation and test sets are never resampled, oversampled, or weighted. Evaluation represents raw, unskewed test performance.

---

## 7. XGBoost Classifier Configuration

The classifier uses XGBoost with histogram-based tree splitting:
- `objective`: `"multi:softprob"`
- `num_class`: 6
- `tree_method`: `"hist"` (native, unbiased handling of NaNs without zero-imputation)
- `eval_metric`: `"mlogloss"`
- `max_depth`: 6
- `n_estimators`: 200
- `learning_rate`: 0.1
- `random_state`: 42

---

## 8. Missing Data & Insufficient Data Handling

In sensor dropout or multi-sensor failure scenarios, residual channels contain `NaN`.
- XGBoost natively routes missing values down optimal tree branch paths.
- Residuals are **never** imputed with 0.0 (a missing reading is physically distinct from zero error).
- **Data Quality Threshold:** If fewer than 4 of the 7 core residuals are valid, `DiagnosisDataQuality.INSUFFICIENT_DATA` is flagged, preventing false confidence.

---

## 9. Evaluation Methodology

### 9.1 Primary Metric: Macro F1
Due to class imbalance, **Six-Class Macro F1** on the held-out test set is the primary performance benchmark. Macro F1 assigns equal weight to each fault type.

Target: Macro F1 ≥ 0.70 (aspirational engineering target on synthetic physics profiles).

### 9.2 Comprehensive Evaluation Output
- Per-class Precision, Recall, F1, and Support
- 6×6 Confusion Matrix
- False alarm rate on nominal data (`none`)
- SENSOR_FAULT recall across diverse failure modes

---

## 10. Feature Importance vs Per-Sample Attribution

The pipeline exposes `model_feature_importance` computed from global tree split gain.

> [!CAUTION]
> Global feature importance represents what the tree ensemble relies on across the entire training space. It is **NOT** per-sample causal explanation and **NOT** SHAP attribution. Per-sample SHAP analysis is deferred to the dedicated Explainability phase.

---

## 11. Phase 7 & Phase 8 Decoupling

Phase 7 and Phase 8 maintain strict modular boundaries:
- The classifier functions completely independently without Phase 7.
- An optional integration pipeline (`FaultDiagnosisPipeline`) can consume Phase 7 anomaly flags:
  - When `anomaly_status == "NORMAL"`, the pipeline can bypass heavy classifier inference and output nominal status.
  - When `anomaly_status in ("WARNING", "ANOMALY")`, full multi-class diagnosis is triggered.
