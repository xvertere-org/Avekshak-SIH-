# NIRVANAA / SIH26054 — Complete Codebase Solution Audit

> **AI-Enabled Real-Time Digital Twin System for Health Monitoring, Fault Prediction and Mission Reliability Enhancement of Aero Piston Engines used in MALE UAVs**

---

## A. Executive Summary

The NIRVANAA-SIH-SUBMISSION repository implements a **complete, end-to-end simulation-based Digital Twin and Prognostics & Health Management (PHM) pipeline** for a hypothetical MALE-UAV aero-piston engine. The system runs entirely on **synthetic telemetry** generated by a **reduced-order, lumped-parameter, grey-box physics engine simulator** loosely anchored to the publicly documented Rotax 912 ULS / 914 F specification.

The pipeline processes telemetry through **13 consecutive phases**: simulator → telemetry ingestion → digital twin state estimation → anomaly detection → fault diagnosis → health indexing → forecasting → remaining useful life (RUL) → explainability → operator advisory, with the output consumed by a **Streamlit dashboard**. Phase 14 adds replay, reporting, and what-if comparison capabilities.

### The Entire Project in One Sentence
> **A physics-informed Digital Twin and AI-powered PHM platform that simulates aero-piston engine behaviour, generates telemetry, compares actual and expected behaviour, detects and diagnoses faults, forecasts degradation using multivariate time-series modelling, estimates health and time to a simulated failure criterion, and converts the results into explainable mission-aware maintenance decision support.**

**Key facts:**
- All data is **synthetic**. No real aircraft telemetry, OEM engine models, or certified flight data exist in the repository.
- The XGBoost fault classifier and Isolation Forest anomaly detector are trained **at runtime** on synthetic simulator-generated data (deterministic bootstrap).
- TimesFM-3 pretrained weights are **loaded** (`LOADED_PRETRAINED` on CUDA via `HF_TOKEN`). Phase 10 forecasting uses the **Google TimesFM-3 foundation model** as the primary forecaster, with Causal EWMA as a verified fallback.
- RUL values are **project-defined functional-failure projections**, not measured remaining life.
- The dashboard is a **decision-support tool**, explicitly not a certified safety system.
- No external datasets are actually loaded or used for training — adapters exist but data directories contain only `.gitkeep` files.

**Physical Relationship Causal Chains:**
The simulator enforces closed-loop thermodynamic and mechanical couplings:
```text
Altitude / Ambient Temp ──> Air Density (ISA) ──> Volumetric Efficiency & Cooling Heat Transfer
Throttle ──> Engine Load ──> Fuel Injection (Willans) ──> Combustion Torque ──> RK4 RPM Dynamics
Heat Generation − Heat Rejection (Convective/Airspeed) ──> Thermal Lumped Mass ──> CHT & EGT
RPM Dynamics + Oil Thermal State ──> Oil Viscosity ──> Oil Pressure & Oil Temperature
RPM + Mechanical Degradation Multipliers ──> Harmonic Synthesis (1×, 2× Orders) + Broadband Noise ──> Vibration RMS
```

**Subsystems implemented:**
| Subsystem | File | Method |
|---|---|---|
| Atmosphere | `subsystems/atmosphere.py` | ISA model: T, P, ρ vs altitude with lapse rate |
| Rotational Dynamics | `subsystems/dynamics.py` | RK4 integration: torque balance (combustion − load − friction) |
| Fuel | `subsystems/fuel.py` | Willans-line: `ṁ = a·P + b`, with lean/rich fault scaling |
| Thermal (CHT/EGT) | `subsystems/thermal.py` | Lumped capacitance (CHT), first-order lag (EGT) |
| Lubrication | `subsystems/lubrication.py` | Oil temp thermal balance, oil pressure = f(RPM, temp) |
| Vibration | `subsystems/vibration.py` | 1×+2× harmonic synthesis + broadband noise |

**Parameter Tier Classification (`config.py`):**
- **Tier A** — Published references (max RPM 5800, max continuous power 58 kW, ISA constants)
- **Tier C** — Calibration parameters (inertia 0.28 kg·m², fuel flow Willans coefficients, thermal capacitances, sensor noise std)
- **Tier D** — Engineering assumptions (efficiency polynomial, airspeed proxy, mechanical condition)

> [!IMPORTANT]
> The simulator is **NOT** validated against real engine telemetry. It is a **synthetic simulation** for demonstration purposes. Parameters are engineering estimates, not measured values.

### Phase 4A–4F — Fault & Degradation Interface

| Property | Detail |
|---|---|
| **Status** | IMPLEMENTED |
| **Files** | [`simulator/fault_interface.py`](file:///d:/NIRVANAA-SIH-SUBMISSION/simulator/fault_interface.py), [`simulator/sensor_faults.py`](file:///d:/NIRVANAA-SIH-SUBMISSION/simulator/sensor_faults.py) |

**Causal Fault Trajectories:**
Faults are injected dynamically into physics subsystem state equations rather than simply toggling categorical labels. For example, cooling degradation directly degrades heat conductance, which drives CHT accumulation, alters EGT exhaust temperature, elevates oil temperature, and widens thermal residuals:

```text
Cooling Effectiveness ↓ ──> Heat Rejection ↓ ──> CHT ↑ ──> EGT & Oil Temp Drift ──> Thermal Residuals ↑
```

**Fault types implemented:**

| Fault | Subsystem | Physical Effect | Sensor Effect |
|---|---|---|---|
| Cooling Degradation | THERMAL | Reduces cooling conductance → elevated CHT | None |
| Lubrication Degradation | LUBRICATION | Reduces oil pressure, increases oil temp | None |
| Fuel Injection Abnormality | FUEL | Modifies fuel flow + EGT (lean/rich) | None |
| Mechanical Degradation | VIBRATION | Amplifies 1×/2× harmonics + broadband noise | None |
| Sensor Fault | SENSOR | None (physics unaffected) | Bias/drift/noise/stuck/dropout on any channel |

Faults are injected via `FaultSchedule` → `FaultState` contracts with time-of-onset, severity ramp, and affected subsystem. Sensor faults bypass physics entirely and modify only the observation layer.

**Data Quality Pipeline Stages (`telemetry/quality.py`):**
Before telemetry reaches downstream feature extraction or digital twin processing, it undergoes 8 verification stages:
1. **Schema Validation**: Validates datatypes, required channels, and provenance metadata.
2. **Timestamp Monotonicity**: Rejects non-increasing timestamps and detects duplicate timesteps.
3. **Missing-Value Detection**: Traps NaNs, dropouts, and empty fields.
4. **Physical-Bound Checking**: Checks values against hard operational envelopes (flags excursion warnings vs rejecting physically impossible readings).
5. **Channel Synchronization**: Synchronizes disparate sampling timestamps onto standard intervals.
6. **Duplicate Detection**: Discards identical repeated packets without processing.
7. **Filtering**: Suppresses high-frequency sensor noise.
8. **Resampling**: Causally aggregates 10 Hz high-frequency raw telemetry into canonical 1.0 Hz frames using RMS downsampling for vibration.

**Prototype-to-Real Telemetry Ingestion Migration Path:**
The ingestion architecture uses an abstract `TelemetryStreamer` interface so that the upstream physical data source can transition from synthetic simulation to physical flight avionics without changing downstream code:

```text
MVP ARCHITECTURE (CURRENT):
Simulator ──> CanonicalTelemetryFrame ──> Ingestion Pipeline ──> Digital Twin & PHM

FUTURE PHYSICAL FLIGHT DEPLOYMENT:
Physical Engine Sensors ──> ECU / FADEC ──> CAN Bus ──> Edge Gateway ──> Telemetry Interface ──> Digital Twin & PHM
```

### Phase 6 — Digital Twin State Estimation & Residual Generation

| Property | Detail |
|---|---|
| **Status** | IMPLEMENTED |
| **Files** | [`digital_twin/twin_model.py`](file:///d:/NIRVANAA-SIH-SUBMISSION/digital_twin/twin_model.py), [`digital_twin/residuals.py`](file:///d:/NIRVANAA-SIH-SUBMISSION/digital_twin/residuals.py) |

**Architecture:** `DigitalTwinModel` independently predicts expected nominal engine states from observable operating conditions (throttle, altitude, ambient temperature, mission phase). **Observed sensor values (RPM, CHT, etc.) are NEVER used as inputs** — ensuring complete sensor fault isolation.

**Expected state prediction chain:**
1. **Atmosphere** → density factor
2. **RK4 rotational dynamics** → expected RPM, power, load
3. **Willans-line** → expected fuel flow (L/h)
4. **Lumped capacitance** → expected CHT (first-order ODE)
5. **First-order lag** → expected EGT
6. **Oil thermal balance** → expected oil_temp, oil_pressure
7. **Harmonic synthesis** → expected vibration RMS

**Residual computation:** `residual = observed − expected` for each of the 7 channels. Residuals are then normalized (divided by channel-specific baseline standard deviations) to produce `*_norm_residual` columns.

### Phase 9 — Health Index & Causal Degradation Tracking

| Property | Detail |
|---|---|
| **Status** | IMPLEMENTED |
| **Files** | [`health_index/`](file:///d:/NIRVANAA-SIH-SUBMISSION/health_index/) (`calculator.py`, `pipeline.py`, `degradation.py`, `smoothing.py`, `schema.py`) |

**Health Index formula:**
```
d_i = clamp((|r_i| − τ_nominal) / (τ_critical − τ_nominal), 0, 1)
degradation = Σ(w_i · d_i)  [over active channels]
HI_raw = 1 − degradation
HI_smooth = α · HI_raw + (1−α) · HI_smooth_prev   [EWMA, α=0.15]
```

**Channel weights:** oil_pressure=0.20, cht=0.18, egt=0.16, oil_temp=0.16, vibration=0.14, rpm=0.10, fuel_flow=0.06.
**τ_nominal = 1.5σ**, **τ_critical = 5.0σ**.

**Health states:** HEALTHY (≥0.85), DEGRADED (≥0.60), SEVERELY_DEGRADED (≥0.35), CRITICAL (<0.35).

**Sensor isolation:** Deterministic heuristic isolates a single channel if it exhibits |r| ≥ 4.5σ while all others are ≤ 1.2σ for ≥ 5s continuously, OR if Phase 8 diagnoses `sensor_fault` with confidence ≥ 0.60.

### Phase 11 — Authoritative RUL & Prognostics

| Property | Detail |
|---|---|
| **Status** | IMPLEMENTED (Synthetic Simulation Estimates) |
| **Files** | [`prognostics/`](file:///d:/NIRVANAA-SIH-SUBMISSION/prognostics/) (`pipeline.py`, `trajectory.py`, `threshold.py`, `uncertainty.py`, `schema.py`) |

**RUL = Remaining Useful Life.** Estimated time until Health Index crosses the EOL (End-of-Life) threshold.

**State machine (exhaustive, no gaps):**

| Condition | Status | RUL Value |
|---|---|---|
| Elapsed < 30s | `INSUFFICIENT_HISTORY` | None |
| Valid channels < 4 | `INSUFFICIENT_DATA` | None |
| Immediate EOL breached | `CRITICAL_EOL_REACHED` | 0.0s |
| HI ≥ 0.85 & slope > 0.0005 | `RECOVERING` | None |
| HI ≥ 0.85 & −0.001 ≤ slope ≤ 0.0005 | `NOT_DEGRADING` | None |
| HI < 0.85 & slope > 0.0005 | `RECOVERING` | None |
| HI < 0.85 & −0.0005 ≤ slope ≤ 0.0005 | `INDETERMINATE_TREND` | None |
| Active degradation (slope sufficiently negative) | `ACTIVE_DEGRADATION` | Calculated |

**Slope estimation:** Theil-Sen robust regression over sliding window (60s default).

**Monte Carlo uncertainty (500 samples):**
1. Perturb anchor HI: `δ_HI ~ N(0, 0.02²)`
2. Perturb slope: `δ_β ~ N(0, SE(β)²)`
3. Perturb EOL threshold: `HI_EOL ~ U(0.33, 0.37)`
4. Solve analytically for each realization
5. Report P05, P50 (median), P95

**EOL criteria (project-defined, NOT OEM/FAA):**
- Health Index ≤ 0.35
- CHT ≥ 150°C
- Oil Pressure ≤ 1.2 bar
- Oil Temp ≥ 140°C
- Vibration ≥ 3.5g

> [!WARNING]
> RUL values are **synthetic simulation estimates** based on project-defined failure criteria. They are NOT measured remaining life, OEM limits, or certified safety margins.

## J. New-Team-Member Briefing

### What problem are we solving?

MALE UAVs (Medium Altitude Long Endurance Unmanned Aerial Vehicles) use piston engines for long-duration ISR missions. If the engine degrades mid-mission (overheating, oil pressure drop, injector clog), the UAV can crash. Traditional monitoring uses simple threshold alarms ("CHT too high!") but can't predict *when* failure will happen or explain *why*.

### What does our system do differently?

We built a **Digital Twin** — a software model that runs alongside the real engine, predicting what healthy readings *should* look like. By comparing actual sensor data against the Digital Twin's predictions, we can detect subtle faults early, before they trigger emergency alarms. Then we diagnose the fault type, estimate how much life remains, and explain the reasoning to the operator.

### How does it work (simple version)?

1. **Simulator** generates realistic engine data with optional faults
2. **Digital Twin** predicts what "healthy" readings should be
3. **Anomaly Detection** notices when actual readings deviate
4. **Fault Diagnosis** identifies which type of fault it is
5. **Health Index** quantifies overall engine health (1.0 = perfect, 0.0 = failed)
6. **Forecasting** predicts where readings will go next
7. **RUL** estimates how many seconds until the engine reaches functional failure
8. **Explainability** explains *why* the system thinks there's a problem
9. **Dashboard** shows everything to the operator in real-time

### What data is synthetic?

**All of it.** The current system generates all telemetry from our physics simulator. No real aircraft data exists in the repository. The simulator uses publicly available Rotax engine specifications as a reference anchor, but it is not a certified model.

### What remains incomplete?

- External dataset integration (adapters exist, data not downloaded)
- Real engine calibration and validation
- Dashboard automated testing

### How would real UAV telemetry be connected?

The `TelemetryRecord` schema accepts data from any source. A real integration would:
1. Implement a `RealTimeTelemetryAdapter` that maps UAV data-link fields to the canonical schema
2. Replace the simulator with the live data feed
3. Calibrate the Digital Twin against actual engine test-bench data
4. Validate thresholds against OEM operating manuals
